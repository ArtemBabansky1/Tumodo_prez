## 0. Суть проекта

Мы строим репозиторий, который превращает текстовое содержание в готовую презентацию в фирменном стиле компании.

Рабочий цикл после настройки будет таким:

1. Я кладу в папку `input/` обычный `.md`-файл с содержанием слайдов.
2. Даю команду собрать презентацию.
3. Ты собираешь презентацию **в двух возможных форматах**:
   - **HTML** — свёрстанные слайды 1920×1080, пиксель-перфект по дизайн-системе (основной формат);
   - **Figma** — та же презентация, созданная в файле Figma через Figma MCP (когда нужна доработка руками дизайнера).
4. Единый стиль гарантируется дизайн-системой, зашитой в проект, и правилами из `CLAUDE.md`.

Первоисточник фирменного стиля — **Figma**. Там уже сделаны: логотип, иконки, цвета, шрифты, сетки, паттерны, мокапы, примеры слайдов. Ты обязан прочитать и понять правила дизайна из Figma через **Figma MCP-сервер** и перенести их в проект в виде токенов, ассетов и текстовых правил.

**Бренд один.** Мультибрендовость не закладываем, но структура должна быть аккуратной, чтобы при желании её можно было расширить.

## 1. Что считается готовым проектом (Definition of Done)

Проект готов, когда:

1. Существует полная структура папок (раздел 3) и `CLAUDE.md` с правилами.
2. Дизайн-система заполнена: токены (цвета, типографика, сетка, отступы, эффекты) вытянуты из Figma; ассеты (логотип, иконки, паттерны, мокапы) выгружены в папки; фото каталогизированы; для каждой категории написан md-файл с правилами использования.
3. Написаны правила построения презентаций и библиотека макетов слайдов (раздел 5).
4. Работает сборка: из `input/_example.md` собирается тестовая презентация в HTML (открывается в браузере, выглядит по фирменному стилю) и та же презентация генерируется в Figma.
5. Я подтвердил, что тестовая презентация соответствует фирменному стилю.

## 4. Этап 2 — импорт дизайн-системы из Figma (делаем вместе, по шагам)

Это самый важный этап. Работаем **строго по одному шагу за раз**: ты делаешь шаг → показываешь результат → я подтверждаю или правлю → только потом следующий шаг. После каждого шага обновляй `PROGRESS.md` и `design-system/MANIFEST.md`.

Общий алгоритм каждого шага:

1. Я даю ссылку на Figma (страница/фрейм с нужной частью дизайн-системы). Ты фиксируешь её в `figma/FIGMA-SOURCES.md`.
2. Читаешь дизайн через Figma MCP: структуру и значения (design context, переменные/variables, скриншоты для самопроверки).
3. Записываешь результат в проект: токены → в `design-system/tokens/`, ассеты → выгрузка файлов в нужные папки, правила → в соответствующий `*-RULES.md`.
4. Показываешь мне краткую сводку: что вытянул, что записал, что выглядит подозрительно или чего не хватает. Задаёшь вопросы, если в Figma неоднозначно.

## 5. Этап 3 — правила презентаций

Когда дизайн-система заполнена, вместе пишем четыре документа в `rules/`. Черновики предлагаешь ты — на основе того, что увидел в Figma (примеры слайдов), и лучших практик; финальные формулировки утверждаю я.

### 5.1 `presentation-rules.md` — как строится презентация

- Обязательный скелет: титульный слайд → (контекст/проблема) → содержание → разделы с разделителями → выводы/CTA → финальный слайд с контактами.
- Правила ритма: сколько слайдов подряд может быть текстовых, когда обязательна визуальная пауза (фото/паттерн/цифры).
- Когда какой тип слайда использовать (текст, цифры, схема, цитата, фото, мокап).

### 5.2 `slide-layouts.md` — библиотека макетов

Для каждого макета: имя-идентификатор, схема зон (где заголовок, где контент, где визуал), правила наполнения (максимум буллетов, размер заголовка), какие ассеты допустимы. Минимальный набор макетов:

`title`, `section-divider`, `agenda`, `text-1col`, `text-2col`, `bullets+image`, `full-image`, `quote`, `kpi-numbers` (2–4 больших числа), `comparison` (2 колонки «до/после»), `timeline`, `team` (фото людей), `mockup-showcase`, `chart`, `contacts/final`.

Каждому макету соответствует HTML-шаблон в `templates/html/layouts/` (этап 4) и описание сборки в Figma в `templates/figma/FIGMA-TEMPLATES.md`.

### 5.3 `style-guide.md` — стиль и дизайн

- Композиционные принципы бренда (воздух, выравнивание, иерархия).
- Do / Don't списком: что запрещено (растягивать лого, ставить текст на пёстрое фото без подложки, использовать цвета вне палитры, более N шрифтовых размеров на слайде и т.п.).
- Правила сочетания фонов: какие слайды тёмные, какие светлые, когда используется акцентный фон.

### 5.4 `content-rules.md` — правила текста

- Максимальные длины: заголовок ≤ N слов, буллет ≤ N слов, максимум M буллетов на слайд.
- Правила: заголовок формулирует мысль, а не тему («Выручка выросла в 2 раза», а не «Финансовые результаты»).
- Оформление чисел, дат, кавычек, тире по правилам русской типографики.

## 6. Этап 4 — движок сборки и тестовая презентация

### 6.1 HTML-пайплайн (основной)

1. Сгенерируй `templates/html/css/tokens.css` **из** `design-system/tokens/*` (цвета, шрифты, отступы как CSS-переменные). Токены — единственный источник значений: в `layout.css`, `components.css` и шаблонах слайдов «сырые» HEX и px из головы запрещены.
2. Подключи шрифты через `@font-face` из `design-system/fonts/files/`.
3. Сверстай каркас `base.html`: контейнер слайда 1920×1080, навигация клавиатурой, нумерация слайдов, режим «все слайды лентой» для ревью.
4. Сверстай шаблон под каждый макет из `slide-layouts.md`. Каждый шаблон проверь визуально (скриншот через Playwright/Puppeteer) и сравни с примерами из Figma.
5. Напиши `scripts/build`: парсит `input/<имя>.md` → раскладывает контент по макетам → собирает `output/<имя>/index.html` (самодостаточный: ассеты скопированы или заинлайнены).
6. `scripts/export-pdf`: по запросу печатает HTML в PDF 1920×1080 без потерь стиля.

### 6.2 Figma-пайплайн

1. В `templates/figma/FIGMA-TEMPLATES.md` опиши, как каждый макет из `slide-layouts.md` строится в Figma: из каких компонентов дизайн-системы, какие отступы, какие стили.
2. Генерация: по команде создаёшь через Figma MCP новый файл (Figma Slides, если доступен, иначе обычный дизайн-файл с фреймами 1920×1080) и наполняешь его слайдами по тем же правилам и контенту, что и HTML-версия.
3. Используй компоненты/стили из моей библиотеки Figma, где это возможно, а не рисуй с нуля.
4. После генерации пришли мне ссылку на файл и скриншоты 2–3 ключевых слайдов для проверки.

### 6.3 Тестовая презентация

1. Создай `input/_example.md` — реалистичный пример на 10–12 слайдов, покрывающий все основные макеты (титул, разделитель, буллеты, цифры, цитата, фото, мокап, финал).
2. Собери её в HTML, сделай скриншоты всех слайдов, покажи мне.
3. Собери её же в Figma.
4. Итерируем, пока я не подтвержу: «стиль соответствует». Все найденные правки фиксируй не только в вёрстке, но и в правилах (`rules/`, `*-RULES.md`), чтобы ошибка не повторялась.

## 7. Рабочий процесс после настройки

### 7.1 Как я запускаю сборку

1. Кладу файл, например `input/pitch-q3.md`.
2. Пишу: «собери pitch-q3» (или `/build pitch-q3`).
3. Ты: парсишь файл → для каждого слайда выбираешь макет из библиотеки (мои пометки `layout:` имеют приоритет) → собираешь HTML → показываешь скриншоты → после правок по запросу: PDF и/или версия в Figma (`/push-figma pitch-q3`).

### 7.2 Формат входного md-файла

Формат должен оставаться простым — «содержание, а не вёрстка». Раздели слайды `---`. Всё оформление — твоя работа по правилам проекта. Пример для `input/_example.md`:

```markdown
---
title: Название презентации
subtitle: Подзаголовок
author: Имя / компания
date: 2026-08-04
lang: ru
---

# Заголовок первого слайда
[layout: title]

---

# Проблема
[layout: bullets+image]
[image: photos/people/team-meeting-01.jpg]

- Первый тезис
- Второй тезис
- Третий тезис

---

# Выросли в 2 раза за год
[layout: kpi-numbers]

- 2x — рост выручки
- 87% — удержание клиентов
- 14 — новых рынков

<!-- notes: комментарий для докладчика, в слайд не попадает -->
```

Правила обработки входного файла:

- Пометки `[layout: ...]`, `[image: ...]` **опциональны**: если их нет, ты сам выбираешь макет и ассеты по правилам из `rules/` и каталогам ассетов.
- Если контент слайда нарушает `content-rules.md` (слишком длинно, слишком много буллетов) — предложи сокращение, но окончательное решение за мной.
- Фото и иконки берутся **только** из `design-system/`. Если подходящего ассета нет — скажи об этом и предложи, что доложить в библиотеку. Никаких стоков и сгенерированных картинок без моего явного запроса.

## 8. CLAUDE.md — что в нём должно быть

`CLAUDE.md` — главный файл, который ты будешь читать в каждой сессии. Создай его на этапе 1 (черновик) и дополняй после каждого этапа. Обязательное содержимое:

1. **Роль**: «Ты — дизайн-технолог фабрики презентаций. Собираешь презентации строго в фирменном стиле по дизайн-системе проекта».
2. **Карта проекта**: краткое описание всех папок и ключевых файлов (куда смотреть за токенами, ассетами, правилами).
3. **Порядок работы над презентацией**: прочитать `rules/*` → прочитать входной md → выбрать макеты → собрать → самопроверка → показать пользователю.
4. **Железные правила** (нарушать нельзя):
   - только цвета/шрифты/отступы из токенов; никаких значений «на глаз»;
   - только ассеты из `design-system/`; ничего не скачивать и не генерировать без запроса;
   - не менять файлы дизайн-системы и правил при сборке презентаций (сборка только читает);
   - готовые файлы — только в `output/<имя-презентации>/`;
   - вопросы вместо догадок при любой неоднозначности контента.
5. **Чек-лист самопроверки перед сдачей** (раздел 9, команда `/check-deck`).
6. **Статус проекта**: ссылка на `PROGRESS.md` — с чего начинать новую сессию, если настройка ещё не завершена.

## 9. Слэш-команды (`.claude/commands/`)

Создай команды-инструкции, чтобы рутинные операции запускались одной строкой:

- **`/import-figma <ссылка> <категория>`** — выполнить шаг импорта из раздела 4 для указанной категории (colors, typography, grid, logo, icons, patterns, mockups, photos, layouts).
- **`/build <имя>`** — собрать HTML-презентацию из `input/<имя>.md`, показать скриншоты слайдов.
- **`/push-figma <имя>`** — сгенерировать/обновить эту презентацию в Figma, вернуть ссылку и скриншоты.
- **`/check-deck <имя>`** — прогнать чек-лист качества по готовой презентации и выдать отчёт: что ок, что нарушено, что исправить.

Чек-лист `/check-deck` (минимум): все цвета из палитры; шрифты и размеры из токенов; сетка и поля соблюдены; логотип по правилам; на каждом слайде не превышены лимиты текста; у фото/иконок есть источник в дизайн-системе; нумерация и финальный слайд на месте; скриншоты слайдов просмотрены тобой на визуальные поломки (переполнение текста, наезды, обрезки).

## 10. Общие правила работы по этому ТЗ

1. **Поэтапность.** Этапы 1 → 2 → 3 → 4 идут последовательно. Внутри этапа 2 — шаг за шагом по таблице. Следующий этап/шаг — только после моего подтверждения.
2. **`PROGRESS.md` всегда актуален.** В начале каждой сессии читай его и говори мне, на чём мы остановились и что предлагаешь делать дальше.
3. **Язык.** Все правила, документация и общение — на русском. Имена файлов, папок, CSS-переменных и код — на английском.
4. **Не переусложняй.** Минимум зависимостей; всё, что можно сделать статикой и простыми скриптами, делаем статикой и простыми скриптами.
5. **Правки — в правила.** Каждое моё дизайнерское замечание фиксируй в соответствующем файле правил, чтобы оно применялось во всех будущих презентациях.
