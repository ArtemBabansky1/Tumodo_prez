# Перенос готовой презентации в Figma

> Обязательный контракт экспорта. Зафиксирован по правкам пользователя
> 2026-08-17. Любое нарушение ниже блокирует статус success.

## 1. Направление и источник истины

1. Сначала агент полностью собирает и проверяет презентацию на платформе.
2. Только готовая презентация из `output/<имя>/` переносится в Figma по кнопке
   платформы. Figma не является источником для обратной сборки в этом сценарии.
3. Исходная презентация на платформе при экспорте не изменяется.
4. Для каждого слайда используется отдельная служебная страница
   `figma-export.html?deck=<имя>&slide=<N>`. Ручная перерисовка и подмена ассетов
   запрещены.

## 2. Ссылка на Figma

- Принимается ссылка на `figma.com/design/...` или `figma.com/file/...`, включая
  ссылку на существующую SECTION.
- Вставленный пользователем служебный префикс `@`, Markdown-обрамление и хвостовая
  пунктуация не являются частью URL и должны быть удалены до валидации.
- Экспорт начинается только после извлечения корректных `fileKey` и `node-id`.

## 3. Реальный capture, а не ложный успех

- Каждый слайд захватывается отдельным одноразовым `captureId`.
- После запуска capture статус опрашивается до `completed`. `pending`,
  `processing`, созданная заявка без запуска helper и пустой серый фрейм не
  считаются результатом.
- После `completed` сохраняется ID фактически созданного корневого фрейма.
- Все созданные корневые фреймы явно перемещаются через `appendChild` внутрь
  целевой SECTION. Координаты задаются повторно уже после перемещения.
- Success разрешён только после повторного чтения структуры Figma-файла и
  подтверждения, что все ожидаемые фреймы действительно находятся в SECTION.

## 4. Структура и редактируемость

- Один слайд = один корневой Figma `FRAME` размером ровно **1920×1080**.
- Слайды располагаются слева направо в исходном порядке с промежутком 160px.
- Название фрейма: `01 — <заголовок>`, `02 — <заголовок>` и так далее.
- Импорт выполняется редактируемым DOM-capture. Единый PNG, скриншот всего
  слайда, IMAGE fill вместо структуры или другой плоский результат запрещён.
- В редактируемом фрейме должны присутствовать отдельные текстовые слои и
  отдельные визуальные/векторные узлы. Проверка только внешнего размера фрейма
  недостаточна.

## 5. SECTION

- Целевая SECTION получает точное человекочитаемое название презентации из
  исходного `title`.
- Технический slug каталога, старое имя пустой секции и названия вроде
  «презентации ai» запрещены.
- Повторный экспорт создаёт новую SECTION, чтобы не перезаписывать результат без
  явного решения пользователя.

## 6. Layout grid

Все корневые фреймы используют один переиспользуемый GridStyle с точным именем
`Tumodo / Presentation / 7×7 / 1920×1080`:

| Ось | Type | Count | Alignment | Margin / offset | Gutter |
|---|---|---:|---|---:|---:|
| Columns | COLUMNS | 7 | STRETCH | 120px | 30px |
| Rows | ROWS | 7 | STRETCH | 120px | 25px |

Обе сетки видимы и имеют цвет `#FF0000` с opacity 10%. Сетка назначается через
`GridStyle`/`gridStyleId`; рисовать поверх слайда красные прямоугольники нельзя.

## 7. SVG и изображения

- Каждый исходный локальный SVG до capture превращается в inline `<svg>`.
- В Figma иконки и другие SVG остаются редактируемыми
  `VECTOR`/`BOOLEAN_OPERATION`-контурами.
- PNG-превью и IMAGE fill вместо SVG-иконки запрещены, даже если внешне иконка
  выглядит похоже. Растровыми остаются только исходные фото и 3D PNG/WebP.
- Число подтверждённых корневых SVG-экземпляров должно совпасть с числом SVG в
  исходной презентации на платформе.

## 8. Геометрия контейнеров

- У карточек `process-steps` padding строго **30px со всех сторон**:
  `paddingTop = paddingRight = paddingBottom = paddingLeft = 30`.
- Значение 34px слева или справа является ошибкой импорта и исправляется через
  Figma API до аудита.
- Сетка и карточки не выходят за нижнюю safe area. Для фрейма 1920×1080 с
  margin 120 нижняя граница каждого `process-step` и его дочерней grid-сетки:
  `bottom <= 960px`.
- Проверяется `absoluteBoundingBox` фактических дочерних карточек, а не только
  внешний размер родительского контейнера.

## 9. Типограф после capture

- DOM-capture может заменить U+00A0 обычным пробелом, поэтому после импорта
  повторно запускается типограф по `characters` **всех** Figma `TEXT`-слоёв.
- Перед редактированием загружаются все реально используемые шрифты слоя; стили
  и редактируемость сохраняются.
- Служебные короткие слова из `scripts/lib/typograph.js` связываются со следующим
  словом неразрывным пробелом U+00A0.
- Финальный аудит обязан найти **0** обычных пробелов или табов после таких слов.

## 10. Сглаживание углов

- После capture агент обходит все дочерние узлы SECTION с радиусом больше 0 и
  доступным свойством `cornerSmoothing`.
- Для каждого узла задаётся `cornerSmoothing = 0.6`: Figma Corner smoothing
  **60%**, режим iOS.
- Финальный аудит повторно читает все скруглённые узлы. Допуск — не более 0.001;
  число корректных узлов должно равняться числу проверенных.

## 11. Обязательный финальный аудит

Экспорт получает `FIGMA_STATUS: success` только при одновременном выполнении
всех условий:

- имя SECTION совпадает с названием презентации;
- число вложенных фреймов совпадает с числом слайдов;
- все фреймы редактируемые и имеют размер 1920×1080;
- layout grid подтверждён у каждого фрейма;
- padding и нижние bounds всех process-карточек подтверждены;
- все скруглённые узлы имеют `cornerSmoothing = 0.6`;
- проверены все TEXT-слои и найдено 0 висячих служебных слов;
- все ожидаемые SVG представлены векторными контурами.

Если хотя бы один счётчик отсутствует, не совпадает с ожидаемым или основан не
на повторном чтении Figma-файла, результат — `FIGMA_STATUS: failed`.
