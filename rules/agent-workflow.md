# Рабочий процесс агента презентаций

Этот файл определяет поведение агента внутри платформы. Пользователь сообщает цель
или прикладывает файл со структурой и контентом. Пользователь не обязан выбирать
макеты, каноны, темы и ассеты до первой сборки.

## 1. Результат первого запуска

Агент автономно проходит весь цикл:

1. Читает все приложенные файлы целиком и определяет, где находятся структура,
   контент, иллюстрации и ограничения.
2. Формулирует коммуникационную задачу колоды: аудитория, цель, главное сообщение
   и требуемое действие/понимание после просмотра.
3. Определяет роль каждого слайда в истории. Один слайд — одна основная мысль.
4. Сохраняет заданные пользователем порядок и количество слайдов. Менять их можно
   только когда без этого материал не помещается или структура явно отсутствует;
   решение фиксируется в плане.
5. Сам выбирает для каждого слайда:
   - семейство макета;
   - конкретный исходный референс Figma из `design-system/canon/decks/library/`;
   - тему;
   - ассеты из дизайн-системы;
   - композицию текста и визуала.
6. Собирает презентацию, снимает каждый слайд и сравнивает его с выбранным каноном.
7. Исправляет переполнение, слабую иерархию, неверные отступы, случайную пустоту и
   однообразный ритм. Максимум три визуальные итерации на слайд.
8. Только после визуальной проверки возвращает готовый результат в платформу.

До создания плана агент запускает `node scripts/recommend-design.js <имя>`. Скрипт
не принимает дизайнерское решение вместо агента: он превращает 126 слайдов Figma
в короткий смысловой shortlist для каждого слайда. Агент проверяет shortlist
визуально и принимает решение в контексте всей истории.

Нельзя просить пользователя выбрать макет или ассет для первой версии. Вопрос
нужен только при содержательной неоднозначности, которая меняет смысл, факты или
аудиторию презентации.

## 2. План колоды

Перед сборкой агент создаёт `output/<name>/deck-plan.json`:

```json
{
  "name": "deck-name",
  "audience": "Кому показываем",
  "communicationJob": "Что аудитория должна понять или сделать",
  "narrativeArc": "Логика истории",
  "slides": [
    {
      "number": 1,
      "title": "Заголовок",
      "purpose": "Роль слайда в истории",
      "claim": "Одна основная мысль",
      "semanticRole": "problem-solution",
      "compositionFamily": "two-panel",
      "layout": "cover",
      "canonReference": "decks/library/13__855-753.png",
      "figmaNodeId": "855:753",
      "theme": "light",
      "density": "medium",
      "mediaStrategy": "3D-объект поддерживает тезис и занимает правую визуальную зону",
      "assets": ["photos/3d/3d-folder-documents-blue.webp"],
      "rationale": "Почему эта композиция подходит смыслу"
    }
  ]
}
```

План — служебный контракт между агентом, движком и экраном предпросмотра. Его текст
не попадает на слайды.

## 3. Выбор канона

- `design-system/canon/decks/library/catalog.tsv` — полная визуальная память из
  Figma-секции `855:401`: 126 слайдов 1920×1080. Это главный источник композиции.
- `design-system/canon/layouts/` — только десять уже реализованных HTML-семейств.
  Наличие там файла не делает его единственным допустимым дизайном.
- Канон выбирается по смыслу и плотности контента, а не по номеру слайда.
- Сначала определяется `semanticRole`, затем композиционная семья, плотность,
  потребность в визуале и только после этого — конкретный Figma-референс.
- Соседние слайды не должны механически повторять один силуэт.
- Конкретный `canonReference` задаёт композицию один в один: иерархию, геометрию,
  визуальный вес и характер пустоты. Заменяются только контент и подходящие ассеты.
- Если текущий HTML-шаблон не способен воспроизвести выбранный канон, запрещено
  молча откатываться к `title-bullets`. Нужно расширить движок или создать
  сохраняемое переопределение конкретного слайда в
  `input/overrides/<name>/slide-XX.html` и при необходимости `slide-XX.css`.
  Движок автоматически подхватывает эти файлы при каждой следующей сборке.

### 3.1. Визуальная политика

- Фото и/или 3D обязательны минимум на 80% содержательных слайдов колоды.
- `node scripts/recommend-design.js <имя>` возвращает `suggestedAssets`; агент
  обязан рассмотреть их до вёрстки и записать выбранный путь в `assets`, а также
  в `[image: ...]` или `[3d: ...]` исходного markdown.
- Допустимые исключения без изображения: разделитель, короткий манифест и плотная
  сетка, где медиа физически ухудшит читаемость. Каждое исключение получает
  явный rationale в `mediaStrategy`, а не значение `none` без объяснения.
- В одной колоде должны встречаться и фото людей, и 3D/мокапы, если тема это
  допускает. Один и тот же ассет нельзя повторять на соседних слайдах.
- Визуал — структурная зона композиции. Он не накладывается поверх текста и не
  добавляется в последний момент как декоративная заплатка.

## 4. Точечная перегенерация после предпросмотра

После первой сборки пользователь выбирает готовый слайд, канонический референс,
опциональные ассеты и пишет пожелание.

Агент обязан:

1. Считать текущий слайд, его скриншот, контент и запись в `deck-plan.json`.
2. Считать выбранный канон и правила дизайн-системы.
3. Сохранить смысл и факты слайда, если пользователь не просил изменить контент.
4. Изменить только выбранный слайд. Остальные слайды и их файлы не трогать.
   Если канон отличается от существующего шаблона, записать изолированную версию в
   `input/overrides/<name>/slide-XX.html` / `.css`, не изменяя общий шаблон.
5. Переснять выбранный слайд, сравнить с каноном и выполнить до трёх итераций.
6. Обновить его `semanticRole`, `compositionFamily`, `canonReference`,
   `figmaNodeId`, ассеты и rationale в `deck-plan.json`.
7. Вернуть обновлённый результат на тот же экран предпросмотра.

## 5. Критерии готовности

- каждый слайд имеет понятную роль и одну главную мысль;
- содержание адресовано аудитории, а не автору или агенту;
- макет подходит объёму и типу содержания;
- канон воспроизведён по композиции, а не использован как декоративная картинка;
- ассет помогает мысли и не служит случайным заполнителем;
- не менее 80% содержательных слайдов имеют фото и/или 3D; исключения объяснены;
- соседние слайды образуют ритм, но остаются одной системой;
- нет переполнений, обрезок, случайных переносов и конфликтов с мебелью слайда;
- существуют актуальные `index.html`, `deck-plan.json` и скриншоты всех слайдов.
